## 1. Overview

Luna moves with **two arm servos**, driven through [servo_module.py](servo_module.py):

| Servo | Function | BCM GPIO | Physical header pin |
|---|---|---|---|
| Left arm | talking sway, raise/lower, arms-up celebration | GPIO 17 | pin 11 |
| Right arm | wave, handshake, talking sway, raise/lower | GPIO 18 | pin 12 |

> **There is no head servo.** It was removed — GPIO 27 is now free. `servo.nod()` still exists but is a deliberate no-op so old call sites can't crash.

Both run at **50 Hz** (the standard hobby-servo rate). Angles are 0–180°, mapped to a 500–2500 µs pulse (2.5%–12.5% duty — `angle_to_pulse()` / `angle_to_duty()` in `servo_module.py`); this wider range is needed to reach the full sweep on most SG90/MG90-class servos. Rest position is `ARM_REST_ANGLE` (90°) for both.

### Motion contract

Exactly one of these is active at a time — a gesture and the talking sway can never run together:

| Luna's state | Arms |
|---|---|
| Not talking, no gesture | **Completely motionless** — the servos are *released* (no pulse at all) |
| Talking | Small synchronized sway of both arms (±`TALK_SWAY_DEGREES`) |
| "hi" / "hello", or the WAVE gesture | Right arm up, small wiggle held up there, back down |
| "handshake" / "shake my hand" | Right arm out perpendicular to meet the person, 2 s pause, small up/down shakes, back down |

Servos are only driven when `ENABLE_SERVOS = True` in `config.py` **and** a pulse backend is available. Otherwise `servo_module.py` runs in **simulation mode**, so the rest of Luna (face, voice, gestures) works unchanged on a Mac/Windows dev machine.

### Why the servos used to twitch non-stop

Three bugs, all fixed — worth knowing about, because two of them can come back if you change this code:

1. **The pulse never stopped.** The old code started PWM at 90° on boot and then only ever *changed* the duty cycle. A pulsed servo is actively holding, and software PWM is generated by a Python thread — every scheduling hiccup shifts the pulse width and the servo physically chases it. Luna now **releases** a servo once it has arrived and settled (`SERVO_DETACH_AT_REST`), so at rest it receives nothing at all and cannot hunt.
2. **Two threads drove the same pins.** A queue worker ran `wave()` while a separate talk worker swayed those same arms; both wrote to the pin, interleaved. There is now exactly **one** worker thread and one motion at a time.
3. **Moves assumed they started at 90°**, so any move beginning mid-sway snapped there first. Moves now interpolate from the servo's real last-commanded angle.

## 2. Parts list

- **2× standard hobby servos** (SG90 micro servo or similar 5 V, 3-pin PWM, full 0–180° range — the code clamps to 0–180° and assumes that range)
- **External 5 V/6 V servo power supply** (a 4× AA pack, a 5V/2A+ UBEC, or a bench supply) — see the power warning below
- **Common ground wire** between the Pi's GND and the servo power supply's GND
- Jumper wires (female-to-male if wiring straight from the Pi header to servo connectors)
- Optional: a small breadboard or perma-proto board to distribute power/ground to both servos, and a mounting bracket/frame for the arms

## 3. Wiring

Each servo has a standard 3-pin connector:

| Wire colour (typical) | Connects to |
|---|---|
| Orange/yellow (signal) | The servo's BCM GPIO pin (17 / 18 / 27 — see table in §1) |
| Red (VCC) | **External** 5V/6V power rail — *not* the Pi's 5V pin |
| Brown/black (GND) | Common ground — tie the Pi's GND, the servo PSU's GND, and all three servo grounds together |

### ⚠️ Power — don't power servos from the Pi

Do **not** wire servo VCC to the Raspberry Pi's own 5V pins (physical pin 2 or 4). A single SG90 stalling, or both servos moving at once (e.g. `arms_up()`), can draw enough current to brown out the Pi — causing random reboots, SD card corruption, or silent GPIO glitches that look like a software bug but aren't.

Use a separate 5V/6V supply rated for at least ~1.5 A (headroom for both servos moving together), and **always** tie its ground to the Pi's ground — shared ground is required for the PWM signal to be read correctly, even though power comes from a separate source.

### Signal wiring summary

```
Raspberry Pi 5 (40-pin header)          Servos
─────────────────────────────           ──────────────────
GPIO 17 (physical pin 11) ───signal───▶ Left-arm servo
GPIO 18 (physical pin 12) ───signal───▶ Right-arm servo
GND (e.g. physical pin 9) ───────────── Common ground rail ── external PSU GND
                                          │
                          External 5V/6V ─┴── both servo VCC pins
```

## 4. Software setup

### 4.1 Install the GPIO library (Pi only)

`RPi.GPIO` is intentionally **not** in `requirements.txt` — it only builds/works on actual Raspberry Pi hardware, and would break installs on Mac/Windows dev machines.

**Important Pi 5 note:** Luna's `config.py` is pinned to `PI_MODEL = 5`. Classic `RPi.GPIO` does **not** support the Pi 5's new RP1 I/O chip and will fail (or silently misbehave) on it. Use **`rpi-lgpio`** instead — a drop-in replacement that exposes the exact same `import RPi.GPIO as GPIO` API `servo_module.py` already uses, backed by `lgpio`:

```bash
# On the Pi, inside the activated venv:
pip install rpi-lgpio --break-system-packages
```

If real `RPi.GPIO` is already installed, remove it first — the two packages conflict since they both provide the `RPi.GPIO` module name:

```bash
pip uninstall RPi.GPIO -y
pip install rpi-lgpio --break-system-packages
```

(On a Pi 4, real `RPi.GPIO` works fine — `pip install RPi.GPIO --break-system-packages` — but since this project targets Pi 5, `rpi-lgpio` is the recommended path either way.)

### 4.1b Install pigpio (strongly recommended)

`RPi.GPIO` / `rpi-lgpio` generate the servo pulse from a **Python thread**. Whenever the scheduler is busy — and Luna runs vision, gestures, STT and TTS concurrently — the pulse width drifts by tens of microseconds and the servo physically chases that drift. That is the classic "buzzing / twitching a few degrees non-stop" symptom.

`pigpio` generates the same pulse with DMA, entirely outside Python's control, so it doesn't drift:

```bash
sudo apt install pigpio python3-pigpio
sudo systemctl enable --now pigpiod     # must be running; Luna talks to the daemon
```

Luna picks it up automatically (`SERVO_BACKEND = "auto"`) and prints `[SERVO] Using pigpio backend` at startup. If the daemon isn't running it falls back to `RPi.GPIO` with a one-line notice — everything still works, just with more jitter.

### 4.2 Enable servos in `config.py`

```python
# ── Servos ────────────────────────────────────────────────────────────────
ENABLE_SERVOS = True   # False = simulation only, True = servos wired up
```

Leave this `False` while developing off the robot (Mac/Windows, or a Pi with no servos wired yet) — everything else in Luna runs identically either way.

### 4.3 Pin / frequency constants (`servo_module.py`)

If your wiring uses different GPIO pins, update these constants at the top of `servo_module.py` (BCM numbering):

```python
PIN_LEFT_ARM  = 17
PIN_RIGHT_ARM = 18

PWM_FREQ = 50   # Hz — standard servo frequency, don't change unless your servos require it
```

Everything else about the motion is tunable from `config.py` instead — see §4.5 below.

### 4.5 Tuning motion in `config.py`

All of the movement is tunable without touching `servo_module.py`:

| Setting | Default | What it does |
|---|---|---|
| `SERVO_BACKEND` | `"auto"` | `"auto"` / `"pigpio"` / `"rpigpio"` — see [§4.1b](#41b-install-pigpio-strongly-recommended) |
| `SERVO_DETACH_AT_REST` | `True` | Stop pulsing a servo once it has settled, so it is genuinely still. Set `False` only if an arm sags under its own weight |
| `SERVO_SETTLE_SECS` | `0.35` | How long to keep driving after a move before releasing |
| `SERVO_STEP_DELAY` | `0.02` | Interpolation step interval — smaller is smoother but more CPU |
| `SERVO_MIN_PULSE_US` / `SERVO_MAX_PULSE_US` | `500` / `2500` | Pulse range for the full 0–180° sweep. Narrow it (e.g. `600`/`2400`) if an arm strains at an end stop |
| `ARM_REST_ANGLE` | `90` | Arms down at the sides — the motionless default |
| `ARM_UP_ANGLE` / `ARM_DOWN_ANGLE` | `160` / `30` | Raised / lowered positions |
| `TALK_SWAY_DEGREES` | `8` | How far the arms sway while Luna talks. Raise for more animated speech |
| `TALK_SWAY_PERIOD` | `1.6` | Seconds per full sway cycle |
| `WAVE_WIGGLES` / `WAVE_WIGGLE_DEGREES` | `3` / `14` | The wiggle at the top of a wave |
| `HANDSHAKE_ANGLE` | `125` | Arm horizontal, pointing at the visitor — **tune this to your build** |
| `HANDSHAKE_HOLD_SECS` | `2.0` | Pause after offering the hand, before shaking |
| `HANDSHAKE_SHAKES` / `HANDSHAKE_DEGREES` | `3` / `12` | Number and size of the shakes |

`HANDSHAKE_ANGLE` is the one you will almost certainly need to adjust: it must be whatever angle puts the arm out perpendicular to Luna's body on *your* linkage, somewhere between `ARM_REST_ANGLE` and `ARM_UP_ANGLE`.

### 4.4 Behavior summary

| State | What happens |
|---|---|
| `ENABLE_SERVOS = False` | Simulation mode — no GPIO touched, one `[SERVO] <gesture>()` line per gesture |
| `ENABLE_SERVOS = True` + pigpio daemon running | `[SERVO] Using pigpio backend` — DMA-timed pulses, no jitter |
| `ENABLE_SERVOS = True` + no pigpio, `RPi.GPIO`/`rpi-lgpio` importable | `[SERVO] Using RPi.GPIO backend` — software PWM, works but jitters more |
| `ENABLE_SERVOS = True` + neither available | Falls back to simulation with a printed reason — Luna keeps running either way |

On shutdown (Ctrl+C or closing the face window), `main.py` calls `servo.cleanup()`, which returns both arms to `ARM_REST_ANGLE`, stops all pulse output and releases the GPIO cleanly, so pins aren't left driven.

## 5. Testing

### 5.1 Quick per-servo test

With `ENABLE_SERVOS = True` and the Pi wired up, run each gesture directly from a Python REPL (venv activated) to confirm wiring before running all of Luna:

```bash
python3 -c "
from servo_module import servo
import time

servo.wave()           # right arm (GPIO 18)
time.sleep(4)
servo.handshake()      # right arm out, 2s pause, then shakes
time.sleep(7)
servo.arm_up('left')   # left arm (GPIO 17)
time.sleep(2)
servo.arms_up()        # both arms together — also checks power headroom
time.sleep(3)

servo.start_talking()  # the gentle sway Luna uses while speaking
time.sleep(4)
servo.stop_talking()   # arms return to rest, then go completely still
time.sleep(2)
"
```

Watch for: the correct servo moving for each call, smooth motion (not jittery), and no Pi reboot/brownout when `arms_up()` drives both arms at once.

### 5.2 Full run

```bash
source venv/bin/activate
python3 main.py
```

Startup logs should show the servo controller initializing with no `RPi.GPIO not found` warning. Say **"hello"** and wave at the camera — Luna's face should react and the right-arm servo should wave back.

## 6. Troubleshooting

| Symptom | Likely cause / fix |
|---|---|
| `[SERVO] Servos disabled (ENABLE_SERVOS=False)` even though you set it `True` | You edited a stale copy, or didn't restart `main.py` after saving `config.py` — config is only read at startup. |
| `[SERVO] RPi.GPIO not found — falling back to simulation` on the Pi | GPIO library isn't installed in the active venv, or you're on Pi 5 with plain `RPi.GPIO` installed instead of `rpi-lgpio` — see [§4.1](#41-install-the-gpio-library-pi-only). |
| Servo doesn't move at all, but no errors printed | Check signal wire is on the correct BCM pin (not just the correct physical position), and that servo VCC actually has power (measure with a multimeter — a dead/underpowered rail won't show up as a Python error). |
| Servo jitters/buzzes constantly instead of holding position | In order of likelihood: (1) you're on the `RPi.GPIO` software-PWM backend — install pigpio, [§4.1b](#41b-install-pigpio-strongly-recommended); (2) `SERVO_DETACH_AT_REST` was set `False`, so the servo is being held actively while idle; (3) a shared-ground problem (Pi GND not tied to servo PSU GND) or a marginal supply under load — verify against [§3](#3-wiring). |
| Arms move a little while Luna is silent | Should be impossible now — the arms are released when idle. Check that nothing is calling `servo.start_talking()` without a matching `stop_talking()`; `text_to_speech.speak()` pairs them in a `finally:` block. |
| A gesture and the talking sway look like they're fighting | Also should be impossible — one worker thread runs one motion at a time. If you added a new gesture, make sure it goes through `self._enqueue(...)` and never writes to a pin directly. |
| Handshake doesn't point at the person | Tune `HANDSHAKE_ANGLE` in `config.py` — [§4.5](#45-tuning-motion-in-configpy). |
| Repeated waves stack up and play for ages | Fixed — duplicate gestures already queued are dropped, and the queue is capped at 3. |
| Pi reboots or the SD card corrupts when servos move (especially `arms_up()`) | Servos are powered from the Pi's own 5V rail. Move them to a separate 5V/6V supply — see the power warning in [§3](#3-wiring). |
| `RuntimeError` mentioning `/dev/gpiomem` or permissions | Add your user to the `gpio` group: `sudo usermod -aG gpio $USER`, then log out/in (or reboot). |
| Works on Pi 4, fails on Pi 5 with cryptic `lgpio`/chip errors | Confirms the `RPi.GPIO` vs `rpi-lgpio` issue in [§4.1](#41-install-the-gpio-library-pi-only) — Pi 5's GPIO chip needs `rpi-lgpio`. |
| Angles look inverted or the servo strains at one end of travel | Your specific servo's real range may be narrower than 0–180°, or mounted rotated 180°. Adjust the target angles in the relevant method in `servo_module.py` (e.g. swap/clamp the `wave()`/`arm_up()` ranges) rather than changing `angle_to_duty()`. |
